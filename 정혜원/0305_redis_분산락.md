## 1. 분산락(Distributed Lock)이란?

여러 대의 서버(분산 환경)가 공통된 자원(DB, 파일 등)을 사용할 때, **데이터가 꼬이지 않도록 한 번에 하나의 서버만 접근하게 제어**하는 기술.

---

## 2. 왜 레디스(Redis)인가?

보통 자바의 `synchronized`나 `ReentrantLock`은 **단일 JVM(서버 1대)** 내에서만 유효.
서버가 여러 대라면 공통 저장소인 레디스를 활용해 상태를 공유하는 것이 가장 빠르고 효율적.

### 구현 방식 비교

| 방식 | 특징 | 장점 | 단점 |
| --- | --- | --- | --- |
| **MySQL (Named Lock)** | DB의 기능을 사용 | 추가 인프라 비용 없음 | DB 부하 증가, 성능이 느림 |
| **Redis (Lettuce)** | `SETNX` 명령어를 통한 스핀 락 | 구현이 간단함 | 지속적인 재시도(Polling)로 레디스 부하 발생 |
| **Redis (Redisson)** | Pub/Sub 기반 알림 방식 | **효율적임(권장 방식)** | 라이브러리 학습 곡선 |

---

## 3. 핵심 메커니즘: Redisson 방식

실무에서 가장 많이 쓰이는 방식은 **Redisson**.

### ① Pub/Sub (발행/구독) 기반

Lettuce처럼 "락 풀렸니?"라고 계속 물어보는(Spin Lock) 게 아니라, 락을 가진 서버가 **"나 이제 다 썼어!"**라고 신호를 보내면 대기하던 서버들이 그때 비로소 획득 시도. 네트워크 부하 감소.

### ② Watchdog (유효 시간 연장)

로직이 실행 중인데 설정한 락 타임아웃이 지나버리면 락이 풀려버리는 대참사 발생 가능. Redisson은 **Watchdog**이라는 기능이 있어, 로직이 끝나지 않았다면 락 유효 시간을 자동으로 조금씩 연장.

---

## 4. 실전 적용 시 주의사항 (트러블슈팅)

> **⚠️ 가장 흔히 하는 실수: 트랜잭션과 락의 순서**
> `@Transactional`과 분산락을 함께 사용할 때, 락이 트랜잭션보다 먼저 해제되면 안됨.
> 1. **(정상)** 락 획득 ➔ 트랜잭션 시작 ➔ 로직 ➔ 트랜잭션 커밋 ➔ **락 해제**
> 2. **(위험)** 락 획득 ➔ 트랜잭션 시작 ➔ 로직 ➔ **락 해제** ➔ 트랜잭션 커밋
> 
> 
> 2번의 경우, 락은 풀렸는데 DB 커밋이 아직 안 된 찰나에 다른 서버가 들어와서 이전 데이터 읽을 수 있음 => 데이터 정합성 깨짐. (Phantom Read?)

---

## 5. 요약 및 정리 (Cheat Sheet)

1. **언제 쓰는가?** 선착순 이벤트, 재고 관리, 결제 처리 등 데이터 정합성이 생명인 곳.
2. **어떻게 쓰는가?** 가급적 **Redisson** 라이브러리를 사용해 Pub/Sub 방식으로 구현.
3. **꼭 챙길 것:** * `try-finally`로 반드시 락 해제 보장.
* 비즈니스 로직보다 락의 범위를 넓게 설정(트랜잭션 커밋 시점 고려).
* 락 획득 실패 시의 타임아웃과 락 유지 시간 설정.
