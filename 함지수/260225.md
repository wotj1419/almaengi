# Gitlab CI/CD

## 1. CI/CD란?
```
CI = Continuous Integration (지속적 통합)
CD = Continuous Delivery/Deployment (지속적 배포)
```

개발 흐름
```
코드 작성 → Git Push → 자동 빌드 → 자동 테스트 → 자동 배포
            └──── 이 모든 과정을 자동화한 것이 CI/CD ────┘
```

**CI/CD 없을 때**
```
1. 개발자가 코드 작성
2. 직접 서버에 SSH 접속
3. git pull
4. 빌드 명령어 입력
5. 서버 재시작
→ 배포할 때마다 반복... "실수할 가능성 높음!"
```

**CI/CD 있을 때**
```
1. 개발자가 코드 작성
2. Git Push
→ 이후 전부 자동 !!
```

## 2. 핵심 구성 요소

### .gitlab-ci/yml
프로젝트 루트에 위치하는 **파이프라인 설계도**<br/>
이 파일 하나가 전체 CI/CD를 정의함

### Runner
`.gitlab-ci.yml`에 정의된 작업을 **실제로 실행하는 서버**<br/>
EC2에 직접 설치해야 함.

### Pipeline
코드가 Push 됐을 때 실행되는 **전체 자동화 흐름**

```
Pipeline
└── Stages (단계)
    ├── build stage
    │   └── Jobs (작업)
    │       └── build-job
    ├── test stage
    │   └── Jobs
    │       └── test-job
    └── deploy stage
        └── Jobs
            └── deploy-job
```

> Stage는 순서대로 실행되고, 같은 Stage 안의 Job들은 병렬로 실행됨

## 3. .gitlab-ci.yml 구조

```yaml
# 1. 전체 Stage 순서 정의
stages:
  - build
  - test
  - deploy

# 2. 전체 Job에서 공통으로 쓸 변수
variables:
  APP_NAME: "my-app"
  DOCKER_IMAGE: "registry.gitlab.com/my-project/my-app"

# 3. 각 Job 정의
build-job:
  stage: build              # 어떤 stage에 속하는지
  image: docker:latest      # 이 Job이 실행될 Docker 이미지
  script:                   # 실행할 명령어 목록
    - docker build -t $DOCKER_IMAGE .
    - docker push $DOCKER_IMAGE
  only:                     # 어떤 브랜치에서 실행할지
    - main
    - develop

test-job:
  stage: test
  script:
    - npm install
    - npm run test
  except:                   # 이 브랜치에선 실행 안 함
    - main

deploy-job:
  stage: deploy
  script:
    - ssh ubuntu@$EC2_IP "docker pull $DOCKER_IMAGE"
    - ssh ubuntu@$EC2_IP "docker-compose up -d"
  only:
    - main
  when: manual              # 수동으로 실행 (자동 배포 방지)
```

## 4. Variables - 중요!

IP 주소, 비밀번호, API 키 같은 민감한 정보를 코드에 직접 쓰면 절대 안 됨!<br/>
Gitlab CI/CD Variables에 저장하고 파이프라인에서 불러와야 함

```
lab.ssafy.com 프로젝트
→ Settings
  → CI/CD
    → Variables  ← 여기에 저장
```

```yaml
# .gitlab-ci.yml에서 사용할 때
script:
  - ssh ubuntu@$EC2_IP "..."        # $변수명 으로 참조
  - echo $DB_PASSWORD
```

**변수 타입**

| 타입 | 설명 | 용도 |
|------|------|------|
| Variable | 일반 텍스트 변수 | IP 주소, 설정값 |
| File | 파일로 저장되는 변수 | SSH Key, 인증서 |

> EC2 SSH 접속에 필요한 `.pem` 키는 **File 타입**으로 등록해야 함.<br/> Variable 타입으로 등록하면 줄바꿈 처리 문제로 접속이 안 되는 경우가 생길 수 있음

## 5. 브랜치 전략 및 CI/CD 연동

실제 프로젝트에서는 브랜치별로 파이프라인을 다르게 구성함

```
feature/* 브랜치  →  build + test 만 실행
      ↓
develop 브랜치    →  build + test + 개발 서버 자동 배포
      ↓
main 브랜치       →  build + test + 운영 서버 수동 배포
```

```yaml
deploy-dev:
  stage: deploy
  script:
    - ssh ubuntu@$DEV_EC2_IP "docker-compose up -d"
  only:
    - develop                # develop 브랜치에서만

deploy-prod:
  stage: deploy
  script:
    - ssh ubuntu@$PROD_EC2_IP "docker-compose up -d"
  only:
    - main                   # main 브랜치에서만
  when: manual               # 운영은 수동으로!
```

> 운영 서버 배포는 `when: manual` 로 꼭 수동 배포로 설정<br/>
자동으로 운영에 배포됐다가 장애 나는 경우가 실제로 엄청 많음


## 6. 전체 CI/CD 흐름

```
개발자 로컬
    │
    │  git push origin develop
    ▼
lab.ssafy.com (Gitlab)
    │
    │  .gitlab-ci.yml 감지
    ▼
Pipeline 시작
    │
    ├── [build stage]
    │       Docker 이미지 빌드
    │       Gitlab Registry에 Push
    │
    ├── [test stage]
    │       단위 테스트 실행
    │       실패하면 여기서 중단 🛑
    │
    └── [deploy stage]
            EC2에 SSH 접속
            새 이미지 Pull
            컨테이너 재시작
                │
                ▼
           🎉 배포 완료
```

## Gitlab CI/CD 이론 정리

```
Gitlab CI/CD 핵심
├── .gitlab-ci.yml  ← 파이프라인 설계도
├── Runner          ← 실제 실행하는 서버 (EC2에 설치)
├── Pipeline        ← 전체 자동화 흐름
├── Stage           ← 순서대로 실행되는 단계
├── Job             ← 각 단계의 실제 작업
└── Variables       ← 민감 정보 안전하게 관리
```
