# AWS/EC2

## 1. AWS란?

**Amazon Web Services**의 약자<br/>
쉽게 말하면 **컴퓨터, 저장소, 네트워크 등 IT 인프라를 인터넷으로 빌려 쓰는 서비스**

```
예전 방식
└── 서버 직접 구매 → 설치 → 유지보수 → 공간/전기 비용
    (초기 비용 수천만원 + 관리 인력 필요)

AWS 방식
└── 필요한 만큼 빌려서 사용 → 쓴 만큼만 과금
    (신용카드 하나로 몇 분 안에 서버 생성)
```

## 2. 서비스 전체 지도

```
AWS 서비스
│
├── 컴퓨팅
│   └── EC2          ← 가상 서버 (핵심!)
│
├── 스토리지
│   └── S3           ← 파일 저장소 (이미지, 정적 파일)
│
├── 네트워크
│   ├── VPC          ← 가상 사설 네트워크
│   ├── Route 53     ← 도메인 관리
│   └── ELB          ← 로드밸런서
│
├── 보안
│   └── IAM          ← 권한 관리
│
└── 모니터링
    └── CloudWatch   ← 로그 & 알람
```

> 특화 프로젝트에서 실제로 쓸 건 **EC2, S3, VPC, IAM, CloudWatch** 정도

## 3. EC2

### IAM Role
EC2가 다른 AWS 서비스에 접근할 때 필요한 **권한 설정**

```
예시: EC2에서 S3에 파일 업로드하고 싶다
→ EC2에 S3 접근 권한을 가진 IAM Role 붙여줘야 함
→ 코드에 AWS Key 직접 박으면 안 됨
```

```
❌
└── 코드에 AWS_ACCESS_KEY = "AKIA..." 직접 입력
    → Github/Gitlab에 올라가면 해킹당함

✅
└── EC2에 IAM Role 부여
    → 코드 수정 없이 권한 관리 가능
```

### User Data
EC2가 **처음 생성될 때 자동으로 실행되는 스크립트**<br/>
Docker 설치, 환경 설정 등을 자동화 가능

```bash
#!/bin/bash
# EC2 생성 시 자동 실행
apt update
apt install -y docker.io
systemctl enable docker
usermod -aG docker ubuntu
```

> User Data를 잘 활용하면 EC2 새로 만들 때마다 수동으로 세팅 안 해도 됨. 나중에 Terraform이랑 같이 쓰면 인프라 자동화의 핵심

## 4. VPC (Virtual Private Cloud)

AWS 안에 만드는 **나만의 가상 네트워크**

```
# 비유

VPC = 아파트 단지 전체
├── Public Subnet = 외부에서 접근 가능한 공간 (경비실, 주차장)
│   └── EC2 (웹 서버, Nginx) ← 인터넷에서 접근 가능
│
└── Private Subnet = 외부에서 접근 불가한 공간 (각 세대)
    └── EC2 (DB 서버) ← 인터넷에서 직접 접근 불가
```

실제 프로젝트 권장 구조

```
인터넷
    │
    ▼
Internet Gateway
    │
    ▼
Public Subnet
├── Nginx (80, 443)     ← 외부 트래픽 받는 창구
└── Bastion Host        ← SSH 접속용 관문 서버
    │
    ▼ (내부 통신만)
Private Subnet
├── Backend EC2         ← 앱 서버
└── DB EC2              ← 데이터베이스
```

> 6주 프로젝트라면 처음엔 Public Subnet에 전부 올려도 괜찮음. 구조를 단순하게 가져가고, Security Group으로 접근을 제한하는 게 현실적일듯. Private Subnet은 나중에 고도화할 때 적용하면 될 거 같음

## 5. S3 (Simple Storage Service)

**무제한 파일 저장소**<br />
서버 디스크에 파일 저장하면 EC2 재생성 시 날아가는데, S3는 별도로 유지됨

```
S3 주요 용도
├── 이미지/파일 업로드 저장소
├── 프론트엔드 정적 파일 호스팅 (React 빌드 결과물)
├── 로그 파일 장기 보관
└── Docker 이미지 백업
```

```
버킷(Bucket) = S3의 최상위 폴더 단위
객체(Object) = 버킷 안에 저장되는 파일
```

> React 같은 프론트엔드는 EC2 없이 **S3 + CloudFront** 조합으로 배포하면 훨씬 저렴하고 빠르게 운영 가능!

## 6. IAM (Identity and Access Management)

AWS 리소스에 대한 **접근 권한을 관리**하는 서비스

```
IAM 구성요소
├── User    ← 사람 (팀원 각자)
├── Group   ← 팀 단위 권한 묶음
├── Role    ← 서비스에 부여하는 권한 (EC2, Lambda 등)
└── Policy  ← 실제 권한 정의서 (JSON)
```

IAM 설정 예시

```
Admin (나 or 팀장)
└── 모든 권한

Developer Group
├── EC2 접근 권한
├── S3 읽기/쓰기
└── CloudWatch 읽기

EC2 Role
├── S3 접근 권한
└── CloudWatch 로그 쓰기
```

> IAM은 **최소 권한 원칙**이 핵심! 필요한 권한만 딱 주는 게 맞음. 처음엔 귀찮아서 `AdministratorAccess` 다 줘버리는 경우가 많은데, 보안 사고의 주요 원인이 될 수 있음

## 7. CloudWatch

AWS 리소스의 **모니터링 & 알람 서비스**

```
CloudWatch 주요 기능
├── Metrics   ← CPU, 메모리, 네트워크 사용량 수집
├── Logs      ← 앱 로그 수집 및 저장
├── Alarms    ← 특정 조건 초과 시 알람 (이메일, Slack)
└── Dashboard ← 한눈에 보는 모니터링 화면
```

```
# 예시 알람 설정

CPU 사용률 > 80% 이상 → 이메일 알람 발송
디스크 사용률 > 90% → Slack 알람 발송
```

> EC2 기본 메트릭은 무료지만, **메모리 사용률은 기본 제공 안 함**. CloudWatch Agent를 EC2에 설치해야 메모리 모니터링이 가능

## AWS 이론 전체 정리

```
AWS 핵심 이론
├── EC2                ← 가상 서버 (프로젝트 핵심)
│   ├── IAM Role       ← EC2 권한 관리
│   └── User Data      ← 초기 자동 세팅
├── VPC                ← 가상 네트워크
│   ├── Public Subnet  ← 외부 접근 가능
│   └── Private Subnet ← 내부 통신만
├── S3                 ← 파일 저장소
├── IAM                ← 사람/서비스 권한 관리
└── CloudWatch         ← 모니터링 & 알람
```
