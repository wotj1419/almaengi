# Jenkins 기초 이론

## 1. Jenkins란?

오픈소스 CI/CD 자동화 도구로, 소프트웨어 빌드/테스트/배포 파이프라인을 자동화하는 서버 애플리케이션.

```
Jenkins = CI/CD 전용 자동화 서버
```

Gitlab CI/CD와 달리 **독립적인 별도 서버**로 운영되며, 다양한 형상관리 도구(Github, Gitlab, Bitbucket 등)와 연동 가능.

```
Gitlab CI/CD       Jenkins
──────────────     ──────────────
Gitlab 내장    vs  별도 서버 설치
.gitlab-ci.yml     Jenkinsfile
Gitlab 전용        모든 Git 플랫폼 연동 가능
```

> 📝 *현재 신규 프로젝트에서 Jenkins 단독 사용은 줄어드는 추세. Gitlab CI/CD, Github Actions 등 플랫폼 내장 도구로 대체되는 중.*

## 2. Jenkins 아키텍처란?

Jenkins는 **Master-Agent 구조**로 동작.

```
Jenkins Master
├── 파이프라인 스케줄링 및 관리
├── Web UI 제공
├── 빌드 결과 저장
└── Agent에게 작업 분배
        │
        ├── Agent 1 (Linux)  ← 실제 빌드/배포 실행
        ├── Agent 2 (Windows)
        └── Agent 3 (Docker)
```

**Master** → 두뇌. 파이프라인 관리 및 UI 담당
**Agent** → 손발. 실제 빌드/테스트/배포 작업 실행

> 📝 *소규모 프로젝트에서는 Master가 Agent 역할까지 같이 하는 경우도 있음. 단, 권장하지 않는 방식.*

## 3. Jenkinsfile이란?

Jenkins 파이프라인을 코드로 정의하는 파일. 프로젝트 루트에 위치하며 Gitlab의 `.gitlab-ci.yml`과 동일한 역할.

Jenkinsfile 작성 방식은 두 가지.

**Declarative (선언형)** ← 입문자에게 권장
```groovy
pipeline {
    agent any                    // 어떤 Agent에서 실행할지

    environment {
        APP_NAME = "my-app"      // 환경변수 정의
    }

    stages {
        stage('Build') {         // Stage 정의
            steps {
                sh 'docker build -t $APP_NAME .'
            }
        }
        stage('Test') {
            steps {
                sh 'npm run test'
            }
        }
        stage('Deploy') {
            steps {
                sh 'docker-compose up -d'
            }
        }
    }

    post {                       // 파이프라인 종료 후 실행
        success {
            echo '배포 성공!'
        }
        failure {
            echo '배포 실패!'
        }
    }
}
```

**Scripted (스크립트형)** ← 유연하지만 복잡
```groovy
node {
    stage('Build') {
        sh 'docker build -t my-app .'
    }
    stage('Deploy') {
        sh 'docker-compose up -d'
    }
}
```

> 📝 *입문 단계에서는 Declarative 방식으로 시작하는 것을 권장. 구조가 명확하고 오류 처리가 쉬움.*

## 4. Jenkins 플러그인이란?

Jenkins의 핵심 강점. 2,000개 이상의 플러그인으로 거의 모든 도구와 연동 가능.

| 플러그인 | 역할 |
|----------|------|
| Git Plugin | Github, Gitlab 연동 |
| Docker Plugin | Docker 빌드/배포 |
| Slack Notification | 빌드 결과 Slack 알림 |
| Blue Ocean | 파이프라인 시각화 UI |
| Credentials | 비밀번호/키 안전하게 관리 |
| Pipeline | Jenkinsfile 파이프라인 지원 |

> 📝 *플러그인이 많을수록 관리 포인트도 늘어남. 플러그인 버전 충돌로 Jenkins 자체가 먹통 되는 경우가 실제로 발생함. 필요한 것만 설치하는 것을 권장.*

## 5. Jenkins vs Gitlab CI/CD란?

| 항목 | Jenkins | Gitlab CI/CD |
|------|---------|--------------|
| 설치 | 별도 서버 필요 | Gitlab 내장 |
| 유지보수 | Jenkins 서버 직접 관리 | 불필요 |
| 플러그인 | 2,000개 이상 | 상대적으로 적음 |
| 설정 파일 | Jenkinsfile | .gitlab-ci.yml |
| 러닝 커브 | 높음 | 낮음 |
| 멀티 플랫폼 | 가능 (Github, Bitbucket 등) | Gitlab 전용 |
| 비용 | 서버 비용 발생 | 무료 (Runner 서버만) |

```
Jenkins가 유리한 상황
├── 여러 Git 플랫폼을 동시에 연동해야 할 때
├── 복잡한 커스텀 파이프라인이 필요할 때
└── 기존 Jenkins 인프라가 이미 구축된 회사

Gitlab CI/CD가 유리한 상황
├── Gitlab을 이미 사용 중일 때  ← 현재 상황
├── 빠르게 CI/CD를 구축해야 할 때
└── 인프라 관리 리소스가 적을 때
```

> 📝 *현재 프로젝트는 lab.ssafy.com (Gitlab) 기반이므로 Gitlab CI/CD가 최적. Jenkins는 이런 구조가 있다는 것을 알아두는 수준으로 충분.*

## 6. Jenkins 파이프라인 흐름이란?

```
개발자 코드 Push
      │
      ▼
Gitlab Webhook 발송 → Jenkins에 이벤트 전달
      │
      ▼
Jenkins Master
파이프라인 스케줄링
      │
      ▼
Jenkins Agent
      │
      ├── [Build Stage]
      │   소스코드 체크아웃
      │   Docker 이미지 빌드
      │
      ├── [Test Stage]
      │   단위 테스트 실행
      │   실패 시 파이프라인 중단 🛑
      │
      └── [Deploy Stage]
          EC2에 배포
          컨테이너 재시작
                │
                ▼
          배포 완료 + Slack 알림 🎉
```

## Jenkins 이론 정리

```
Jenkins 핵심
├── 정의          ← 독립적인 CI/CD 자동화 서버
├── 아키텍처      ← Master(관리) - Agent(실행) 구조
├── Jenkinsfile   ← 파이프라인 정의 파일 (Declarative 권장)
├── 플러그인      ← 2,000개 이상, 거의 모든 도구 연동 가능
└── 현재 포지션   ← Gitlab CI/CD, Github Actions로 대체되는 추세
```
