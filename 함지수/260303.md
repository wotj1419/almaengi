# Kubernetes (K8s) 기초 이론

## 1. Kubernetes란?

컨테이너화된 애플리케이션의 **배포, 확장, 관리를 자동화**하는 오픈소스 컨테이너 오케스트레이션 플랫폼. Google이 내부 시스템(Borg)을 기반으로 개발하여 오픈소스로 공개.

```
Docker    = 컨테이너 하나를 만들고 실행하는 도구
Kubernetes = 컨테이너 수백~수천 개를 관리하는 도구
```

> 📝 *K8s라고 줄여 부르는 이유 → Kubernetes에서 K와 s 사이 글자가 8개라서 K8s.*

## 2. Kubernetes가 필요한 이유

Docker만으로 운영할 때 발생하는 문제점.

```
문제 상황 1 - 컨테이너가 죽었을 때
Docker : 죽은 컨테이너 직접 확인 후 수동 재시작
K8s    : 자동 감지 후 즉시 재시작 (Self-healing)

문제 상황 2 - 트래픽이 갑자기 몰릴 때
Docker : 수동으로 컨테이너 추가 실행
K8s    : 트래픽 감지 후 컨테이너 자동 증설 (Auto Scaling)

문제 상황 3 - 새 버전 배포할 때
Docker : 서비스 잠깐 중단 후 배포
K8s    : 무중단 배포 (Rolling Update)

문제 상황 4 - 서버가 여러 대일 때
Docker : 어느 서버에 컨테이너 올릴지 수동 결정
K8s    : 서버 상태 보고 자동으로 최적 배치 (Scheduling)
```

## 3. Kubernetes 아키텍처

```
Kubernetes Cluster
├── Control Plane (Master)  ← 두뇌. 전체 클러스터 관리
│   ├── API Server          ← 모든 요청의 진입점
│   ├── Scheduler           ← 어떤 Node에 Pod 배치할지 결정
│   ├── Controller Manager  ← 현재 상태를 원하는 상태로 유지
│   └── etcd                ← 클러스터 전체 상태 저장 DB
│
└── Worker Node (여러 대)   ← 손발. 실제 컨테이너 실행
    ├── kubelet             ← Control Plane 명령 수신 및 실행
    ├── kube-proxy          ← 네트워크 통신 담당
    └── Container Runtime   ← 컨테이너 실제 실행 (Docker 등)
```

> 📝 *Control Plane은 클러스터 관리만 담당. 실제 앱 컨테이너는 Worker Node에서만 실행됨.*

## 4. 핵심 오브젝트

### Pod란?
Kubernetes에서 **배포 가능한 가장 작은 단위**. 하나 이상의 컨테이너 묶음.

```
Pod
└── Container 1 (메인 앱)
└── Container 2 (사이드카 - 로그 수집 등)
    └── 같은 네트워크/스토리지 공유
```

```yaml
# Pod 정의 예시
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
  - name: my-app
    image: my-app:latest
    ports:
    - containerPort: 8080
```

> 📝 *Pod는 직접 생성하지 않는 것을 권장. Pod가 죽으면 재생성이 안 됨. 반드시 Deployment를 통해 관리.*

### Deployment란?
Pod를 **선언적으로 관리**하는 오브젝트. 원하는 상태를 정의하면 K8s가 자동으로 맞춰줌.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3              # Pod 3개 유지
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app
        image: my-app:v2   # 새 버전으로 Rolling Update
        ports:
        - containerPort: 8080
```

```
Deployment 주요 기능
├── Pod 개수 유지 (replicas)
├── Rolling Update (무중단 배포)
└── Rollback (이전 버전으로 즉시 복구)
```

### Service
Pod에 접근하기 위한 **고정된 네트워크 엔드포인트**. Pod는 재생성될 때마다 IP가 바뀌는데, Service는 고정 IP/DNS를 제공.

```
Service 종류
├── ClusterIP    ← 클러스터 내부 통신용 (기본값)
├── NodePort     ← 외부에서 Node IP:Port로 접근
└── LoadBalancer ← 클라우드 로드밸런서와 연동 (AWS ELB 등)
```

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app            # 이 라벨을 가진 Pod로 트래픽 전달
  ports:
  - port: 80
    targetPort: 8080
  type: LoadBalancer       # AWS ELB 자동 생성
```

### Ingress란?
**외부 HTTP/HTTPS 트래픽을 클러스터 내부 Service로 라우팅**하는 오브젝트. Nginx의 리버스 프록시와 동일한 역할.

```
외부 트래픽
    │
    ▼
Ingress (Nginx Ingress Controller)
    │
    ├── /api  → backend-service
    └── /     → frontend-service
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  rules:
  - host: myapp.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: backend-service
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 3000
```

### ConfigMap & Secret이란?
환경변수와 민감 정보를 컨테이너와 **분리해서 관리**하는 오브젝트.

```
ConfigMap ← 일반 설정값 (DB 호스트, 포트 등)
Secret    ← 민감 정보 (비밀번호, API 키 등) - Base64 인코딩
```

```yaml
# ConfigMap 예시
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "database-service"
  DB_PORT: "3306"

# Secret 예시
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
data:
  DB_PASSWORD: "c2VjcmV0MTIz"   # Base64 인코딩된 값
```

> 📝 *Secret은 Base64 인코딩이지 암호화가 아님. 진짜 보안이 필요하면 AWS Secrets Manager 또는 Vault와 연동 필요.*

## 5. kubectl이란?

Kubernetes 클러스터를 조작하는 **CLI 도구**.

```bash
# 기본 명령어 구조
kubectl [동사] [오브젝트] [이름]

# 자주 쓰는 명령어
kubectl get pods                    # Pod 목록 조회
kubectl get pods -o wide            # 상세 정보 포함
kubectl describe pod my-app-pod     # Pod 상세 정보
kubectl logs my-app-pod             # Pod 로그 확인
kubectl exec -it my-app-pod -- bash # Pod 내부 접속
kubectl apply -f deployment.yaml    # 오브젝트 생성/수정
kubectl delete -f deployment.yaml   # 오브젝트 삭제
kubectl rollout undo deployment/my-app  # 이전 버전으로 롤백
```

> 📝 *`kubectl apply`는 파일 기준으로 현재 상태와 비교해서 변경된 부분만 적용. `kubectl create`는 새로 만들 때만 사용. 실무에서는 apply를 주로 사용.*

## 6. AWS에서의 Kubernetes란?

AWS에서는 **EKS (Elastic Kubernetes Service)** 로 K8s를 관리형으로 제공.

```
직접 설치 (Self-managed)
└── Control Plane 직접 설치 및 관리
    → 설정 복잡, 유지보수 부담

EKS (Managed)
└── Control Plane을 AWS가 관리
    → Worker Node만 관리하면 됨
    → 단, 비용 발생 (시간당 약 $0.10)
```

> 📝 *EKS는 비용이 꽤 나옴. 6주 프로젝트에서는 굳이 EKS까지 갈 필요 없음. Docker + Gitlab CI/CD로 충분. K8s는 개념만 알아두고 나중에 실무에서 익히는 것을 권장.*

## 7. 로컬 실습 환경

클라우드 비용 없이 로컬에서 K8s를 연습할 수 있는 도구들.

| 도구 | 특징 | 추천 대상 |
|------|------|-----------|
| minikube | 가장 대중적, 기능 풍부 | 입문자 |
| k3d | 가볍고 빠름, Docker 기반 | 입문자 ← 추천 |
| kind | CI 환경에서 많이 사용 | 중급자 |

```bash
# k3d 설치 및 클러스터 생성 (Mac 기준)
brew install k3d
k3d cluster create my-cluster
kubectl get nodes                   # 클러스터 정상 동작 확인
```

> 📝 *로컬 실습은 k3d가 가장 가볍고 빠름. Docker Desktop이 설치되어 있으면 바로 사용 가능.*

## Kubernetes 이론 정리

```
Kubernetes 핵심
├── 정의          ← 컨테이너 오케스트레이션 플랫폼
├── 필요한 이유   ← Self-healing, Auto Scaling, 무중단 배포
├── 아키텍처      ← Control Plane (두뇌) + Worker Node (손발)
├── 핵심 오브젝트
│   ├── Pod         ← 배포 최소 단위
│   ├── Deployment  ← Pod 선언적 관리
│   ├── Service     ← 고정 네트워크 엔드포인트
│   ├── Ingress     ← 외부 트래픽 라우팅
│   └── ConfigMap/Secret ← 설정/민감정보 분리
├── kubectl       ← 클러스터 조작 CLI 도구
└── AWS EKS       ← 관리형 K8s 서비스 (비용 발생)
```
