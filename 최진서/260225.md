# 6.1 Nested Loop Join

---

### 기본 개념

Nested Loop(NL) 조인은 가장 단순한 조인 방식으로, 이중 반복문과 같은 구조입니다.

- 외부 루프(Outer): 선행 테이블(T1)을 스캔
- 내부 루프(Inner): 선행 테이블의 각 행마다 후행 테이블(T2)에서 일치하는 행을 검색
- 외부 루프(Outer), 내부 루프(Inner) 이해하기
    
    ```java
    // 예시: 고객(Customer)과 주문(Order)을 customer_id로 조인
    
    // 선행 테이블 (Outer)
    List<Customer> customers = getCustomers();
    // 후행 테이블 (Inner)
    List<Order> orders = getOrders();
    
    List<JoinResult> results = new ArrayList<>();
    
    // 외부 루프: 선행 테이블을 한 행씩 스캔
    for (Customer customer : customers) {
    
        // 내부 루프: 선행 테이블의 각 행마다 후행 테이블 전체를 검색
        for (Order order : orders) {
    
            // 조인 조건 비교
            if (customer.getId() == order.getCustomerId()) {
                results.add(new JoinResult(customer, order));
            }
        }
    }
    
    // 만약 T1 의 데이터가 1000, T2 의 데이터가 10000 인 상황에서
    // 지금 코드처럼 인덱스가 없으면 1000000 번의 비교를 해야함.
    ```
    

### 적합한 상황

NL 조인은 **OLTP 업무 환경**에 특히 적합합니다. 이유는 선행 테이블의 추출 건수가 적을수록 성능이 좋기 때문입니다. 즉, **소량 데이터 조인**에 최적화된 방식입니다.

- OLTP 란?
    
    **Online Transaction Processing**의 약자로, **실시간 트랜잭션 처리** 업무 환경을 말합니다.
    
    **대표적인 예시:**
    
    - 은행 계좌이체
    - 온라인 쇼핑몰 주문/결제
    - 항공권 예약
    - 회원가입, 로그인
    
    **주요 특징:**
    
    - **소량의 데이터**를 읽고 쓰는 작업이 대부분입니다 (예: 한 건의 주문 등록)
    - **동시 사용자가 많고**, 빠른 응답 속도가 중요합니다
    - INSERT, UPDATE, DELETE 같은 **변경 작업**이 빈번합니다
    - 데이터 정합성과 무결성이 핵심입니다 (ACID 트랜잭션)

### 핵심 전제 조건

NL 조인의 성능을 위해 **후행 테이블의 조인키에 인덱스가 반드시 필요**합니다. 그림 4-12를 보면, T1의 각 행에 대해 `IDX_T2` 인덱스를 통해 T2에 접근하는 것을 볼 수 있습니다. 인덱스가 없으면 매번 전체 테이블을 스캔해야 하므로 성능이 크게 저하됩니다.

- 인덱스 개념은 3.2 실행계획분석에 정리되어 있음.

### 성능에 영향을 미치는 3가지 요소

1. **선행 테이블의 추출 건수** — 적을수록 좋음 (외부 루프 반복 횟수 결정)
2. **후행 테이블의 반복 조인 횟수** — 최초 추출 건수에 비례
3. **후행 테이블의 인덱스 효율** — 인덱스를 통한 부분 범위 처리가 핵심

### 주의할 점

조인키 컬럼에 인덱스가 없거나, 불필요한 중복 조인으로 조인 횟수가 증가하면 NL 조인이 오히려 성능을 악화시킬 수 있습니다.

### 비효율 최소화를 위한 보완 방법

PostgreSQL은 후행 테이블의 반복 스캔 비효율을 줄이기 위해 다음을 지원합니다:

- **Materialize** — 후행 테이블 결과를 메모리에 저장
- **Memoization** — 같은 조인키 값의 결과를 캐싱
- **Semi/Anti 조인** — EXISTS/NOT EXISTS 최적화
- **Parallel 조인** — 병렬 처리

## 6.1.1 Materialize 조인

>
>
>
> 테이블 데이터는 디스크의 여러 블록과 행에 흩어져 저장되어있다.
>
> Materialize 는 후행 테이블을 처음 1번만 흩어진 상태에서 조회하면서, 메모리 혹은 디스크의 temp 파일에 저장한다. (메모리가 충분하지 못하면 디스크 temp 파일에 저장함)
>

### Materialize가 왜 필요한가?

앞에서 NL 조인은 **후행 테이블에 인덱스가 필요하다**고 배웠죠? 그런데 만약 인덱스가 없다면 어떻게 될까요?

선행 테이블에서 행을 하나 꺼낼 때마다, 후행 테이블을 **처음부터 끝까지 전부 읽어야** 합니다. 선행 테이블이 50만 건이면 후행 테이블을 50만 번 전체 스캔 (50만 x N) 하는 거예요. 디스크 I/O가 어마어마해지겠죠?

**Materialize는 이 문제를 해결하기 위한 방법입니다.** 후행 테이블을 딱 한 번만 읽고, 그 결과를 **메모리(work_mem)에 올려놓는** 것입니다.

### 동작 방식을 비유로 설명하면

학교 시험 채점을 한다고 생각해 보세요.

- **Materialize 없이**: 1반 학생 답안지를 하나 꺼낼 때마다, 창고에 가서 정답지를 꺼내보고, 다시 넣고, 또 다음 학생 답안지에서 또 창고에 가서 꺼내고... (매번 창고 왕복 = 디스크 I/O)
- **Materialize 사용**: 정답지를 **처음에 한 번 복사해서 책상 위에 올려놓고**(= 메모리에 적재), 이후엔 책상 위 것만 보면서 채점 (= 메모리 접근, 훨씬 빠름)

## 예제 분석

### 테스트 환경

- **T1**: 50만 건 (큰 테이블)
- **T2**: 5천 건 (작은 테이블)
- Hash Join과 Merge Join은 꺼두고 NL 조인만 사용하도록 설정 (p.314 맨 아래 코드)

### 메모리가 충분한 경우

(메모리) work_mem 에 저장

`T1 (50만 건, Outer) → Materialize된 T2 (5천 건, Inner)`

여기서 재미있는 점은 **큰 테이블(T1)이 선행**이라는 것입니다. 보통 NL 조인은 작은 테이블이 선행이 유리한데, 왜 그럴까요?

**작은 T2를 메모리에 통째로 올릴 수 있으니까요!** T2(5천 건)를 메모리에 올려놓으면, T1의 50만 건이 반복 접근해도 메모리에서 읽으니 빠릅니다. T2의 Seq Scan은 **loops=1** (딱 한 번만 읽음)인 것을 확인할 수 있어요.

<aside>
💡

T1, T2 중 큰 테이블을 후행 테이블로 work_mem 에 올리는 것이 이론적으로는 가장 효율적인 방법이지만, 현실적으로 (T1)50만 건을 work_mem 에 올리는게 불가능하여 T1, T2 중 work_mem 에 올릴 수 있는 테이블(T2) 중 가장 큰 테이블(T2)을 올린 것이다.

- 옵티마이저의 판단 과정

  [1단계] 이상적인 방법 찾기
  "T1(50만 건)을 메모리에 올리면 가장 빠르겠다"

  [2단계] 현실 확인
  "work_mem = 4MB인데... T1(50만 건)은 안 들어가네..."

  [3단계] 차선책 선택
  "그러면 메모리에 들어가는 것 중 가장 큰 T2(5천 건)를 올리자!"

</aside>

### 메모리가 부족한 경우 (work_mem = 64KB)

(디스크) temp 에 저장

`T2 (5천 건, Outer) → Materialize된 T1 (50만 건, Inner)`

work_mem을 64KB로 아주 작게 설정하면, 메모리에 다 못 담으니 **temp 파일(디스크)**을 사용하게 됩니다. 이때는 조인 순서가 뒤집어져서 **작은 T2가 선행**이 됩니다. 왜냐하면 temp 디스크에 반복 접근하는 횟수를 줄이려면 선행 테이블 건수가 적어야 하기 때문이에요.

<aside>
💡

어차피 디스크에 저장하는건데, 왜 T2(5천)을 선행으로 하는게 좋은걸까? T2 가 선행이든 후행이든 5천 * 50만 읽는거 아닌가?

⇒ 탐색비용과 읽기비용은 다르다 !! (탐색 > 읽기)

탐색(seek) : 한바퀴 돌고 처음 위치로 이동하는 시간

읽기(read) : 처음 위치부터 쭉 읽는 시간

- 예시

  방법 1: seek 5,000번   + read 25억 건
  방법 2: seek 500,000번 + read 25억 건
  ↑
  read는 같지만
  seek 횟수가 100배 차이
  → 이게 속도 차이를 만듦

</aside>

두 결과를 비교하면:

- 메모리 충분: **약 211초** (temp I/O 없음)
- 메모리 부족: **약 430초** (temp I/O 약 4,200만 블록 발생)

**2배 넘게 느려졌습니다.** 그래서 적절한 work_mem 설정이 중요합니다.

### Temp Tablespace

(위에서 공부한, 메모리가 부족한 경우에 저장하는 공간)

메모리에 다 담지 못할 때 사용하는 임시 디스크 공간입니다. SQL이 실행되는 동안만 temp 파일이 생성되고, **SQL이 끝나면 자동으로 삭제**됩니다. 세션마다 별도 파일을 만들어서 서로 영향을 주지 않습니다.

## 핵심 정리

| 상황 | 동작 | 성능 |
| --- | --- | --- |
| 후행 테이블에 인덱스 있음 | 인덱스로 바로 찾기 | 가장 빠름 |
| 인덱스 없음 + 메모리 충분 | Materialize (메모리) | 괜찮음 |
| 인덱스 없음 + 메모리 부족 | Materialize (temp 디스크) | 느림 |

결국 **인덱스를 잘 만드는 것이 최우선**이고, 그게 어렵다면 **work_mem을 충분히 확보**하는 것이 차선책입니다.

💡

인덱스도 결국 디스크일텐데 왜 Materialize 보다 빠른걸까?

    - 수명
        - work_mem 은 쿼리 시작과 종료
        - shared_buffers 는 PostgreSQL 서버 시작과 종료
- 인덱스 vs Materialize

  ### Materialize (메모리에서 전체 훑기)

  `매 반복마다 10,000건 전부 훑기

  [1바퀴] 메모리에서 10,000건 훑기 ⚡ (메모리라 빠르긴 함)
  [2바퀴] 메모리에서 10,000건 훑기 ⚡
  [3바퀴] 메모리에서 10,000건 훑기 ⚡

  총 30,000건 읽기 (메모리)`

  ### Index Scan (디스크에서 찾기)

  아래는 예시이다. 실제 인덱스 스캔은 처음 한번만 디스크, 이후에는 shared_buffers 에 올리고 접근한다.

  `매 반복마다 B-Tree 3~4단계만 읽기

  [1바퀴] 디스크에서 3~4블록 읽기 🐢 (디스크지만 아주 적은 양)
  [2바퀴] 디스크에서 3~4블록 읽기 🐢
  [3바퀴] 디스크에서 3~4블록 읽기 🐢

  총 9~12블록 읽기 (디스크)`

  ## 핵심: 메모리 많이 vs 디스크 조금

  `Materialize: 메모리에서 30,000건 읽기
  Index Scan:  디스크에서 12블록 읽기

  어느 게 빠를까?`

  `메모리 1번 읽기: 약 100나노초
  디스크 1번 읽기: 약 10,000,000나노초 (10만 배 느림)

  Materialize: 100ns × 30,000 = 3,000,000ns
  Index Scan:  10,000,000ns × 12 = 120,000,000ns

  어? Materialize가 더 빠른데? 🤔`

  ## 그런데! 인덱스도 캐싱돼요

  자주 쓰이는 인덱스 블록은 PostgreSQL이 **shared_buffers(공유 메모리)**에 캐싱해요.

  `첫 번째 접근: 디스크에서 읽음 🐢
  두 번째부터:  캐시에서 읽음 ⚡ (메모리 속도!)

  B-Tree 루트, 브랜치 노드는 거의 항상 캐시에 있음
  → 실제로는 디스크 접근이 거의 없음!`

  `실제 Index Scan:
  [1바퀴] 루트(캐시⚡) → 브랜치(캐시⚡) → 리프(캐시⚡) → 3번 메모리 읽기
  [2바퀴] 루트(캐시⚡) → 브랜치(캐시⚡) → 리프(캐시⚡) → 3번 메모리 읽기
  [3바퀴] 루트(캐시⚡) → 브랜치(캐시⚡) → 리프(캐시⚡) → 3번 메모리 읽기

  총 9번 메모리 읽기!`

  ## 최종 비교

  |  | Materialize | Index Scan (캐시 적중) |
      | --- | --- | --- |
  | 메모리 읽기 횟수 | 30,000번 | 9번 |
  | 디스크 읽기 횟수 | 처음 1번 | 처음 1번 |

  ## 한 줄 요약

  > 인덱스도 디스크에 있지만, **자주 쓰이는 부분은 메모리에 캐싱**돼요. 결국 **메모리에서 30,000번 읽기 vs 메모리에서 9번 읽기**, 인덱스가 압도적으로 빨라요!

## 6.1.2 Memoize 조인

한마디로 **"같은 답을 또 구하지 말고, 기억해뒀다가 재사용하자"**는 기법입니다.

### 비유로 이해하기

수학 시험 감독을 한다고 해봅시다. 50만 명의 학생 답안지를 채점하는데, 문제가 2종류밖에 없어요 (A형, B형).

- **Memoize 없이**: 50만 장 매번 정답지를 꺼내서 대조 → 50만 번 작업
- **Memoize 사용**: A형 정답 한 번 확인하고 기억, B형 정답 한 번 확인하고 기억 → **실제 채점은 2번**, 나머지 499,998번은 기억한 답으로 바로 처리

이것이 바로 예제 1의 결과입니다. Misses: 2 (실제 조인 2번), Hits: 499,998 (캐시에서 재사용).

## Materialize와 뭐가 다른 거야?

| 구분 | Materialize | Memoize |
| --- | --- | --- |
| 방식 | 후행 테이블 **전체**를 메모리에 올림 | 조인 **결과값**만 캐싱 |
| 조건 | 인덱스 없을 때 | 인덱스 있고, 중복값이 많을 때 |
| 비유 | 정답지 전체를 책상에 올려놓기 | 이미 채점한 답을 메모해두기 |

## 필요 조건

Memoize가 작동하려면 몇 가지 조건이 필요합니다.

**조인키의 중복이 있어야 합니다.** 조인키가 전부 유니크하면 캐싱할 의미가 없어요. 매번 새로운 값이니까요. 예제 1에서 `level % 2`로 만들어서 값이 0, 1 두 종류뿐인 이유가 이겁니다.

<aside>
💡

SELECT * FROM t1, t2 WHERE t1.c1 = t2.c1 를 예로 들어보자.

c1 컬럼이 유니크하면 중복된 값을 조회할 수가 없다.

⇒ 캐싱이 의미가 없음

</aside>

**후행 테이블에 인덱스가 있어야 합니다.** 캐시에 없는 값(Miss)이 나왔을 때 인덱스로 빠르게 찾아야 하니까요.

<aside>
💡

인덱스가 없어도 Memoize 쓸 수는 있지만, 그럴거면 옵티마이저는 Materialize 를 선택하므로 인덱스가 Memoize 사용의 필요조건(=필수조건)이다.

</aside>

**통계 정보가 수집되어야 합니다.** 옵티마이저가 "중복이 많으니 Memoize가 효율적이겠다"고 판단하려면 테이블 통계가 필요합니다.

**메모리(work_mem)가 충분해야 합니다.** 캐시를 저장할 공간이 있어야 하니까요.

## 내부 동작 방식

Memoize는 내부적으로 **해시 테이블**을 사용합니다.

<aside>
💡

해시 테이블과 LRU 는 work_mem 에 저장된다.

- 그림 4-14 설명

  ① 후행테이블에서 Key=40인 행을 찾음 (Index Scan)
  후행테이블: col1=40, ... → {40, ZZZ} 발견!

  ② 엔트리 키 리스트에 Key:40 추가 (최근 사용 기록)
  → 맨 앞에 추가됨 (가장 최근에 사용했으니까)

  ③ 해시테이블의 0x13에 {40,ZZZ} 추가
  기존: {40,CCC}, {40,BBB}
  추가: {40,ZZZ}
  → complete가 f(미완료)니까 계속 찾는 중

</aside>

`선행 테이블에서 C1 = 0 을 꺼냄
→ 해시 테이블에 0이 있나? → 없음(Miss)
→ 실제로 후행 테이블에서 조인 수행
→ 결과를 해시 테이블에 저장: {0: 조인 결과}

선행 테이블에서 C1 = 1 을 꺼냄
→ 해시 테이블에 1이 있나? → 없음(Miss)
→ 실제 조인 수행
→ 결과 저장: {0: 결과, 1: 결과}

선행 테이블에서 C1 = 0 을 꺼냄
→ 해시 테이블에 0이 있나? → 있음!(Hit)
→ 조인 안 하고 저장된 결과 바로 반환 ✅

... 이후 499,998건 전부 Hit`

- 이거 뭔소린지 해석

  ## 전체 상황

  `선행 테이블 T1 (50만 건):
  | c1 |
  |----|
  | 0  |  ← 1번째
  | 1  |  ← 2번째
  | 0  |  ← 3번째
  | 1  |  ← 4번째
  | 0  |  ← 5번째
  | 1  |  ← 6번째
  | ... (0과 1이 반복, 각 25만 건)

  후행 테이블 T2 (5천 건, 인덱스 있음):
  | c1 | c2  |
  |----|-----|
  | 0  | AAA |
  | 1  | BBB |
  | 2  | CCC |
  | ... |    |`

  ## 하나씩 따라가기

  ### 1번째: c1 = 0

  `해시 테이블: (비어있음)

  c1=0 들어옴 → 해시 테이블에 0 있나? → 없음! (Miss)
  → 후행 테이블에서 Index Scan으로 c1=0 찾기
  → 결과: {0, AAA}
  → 해시 테이블에 저장 + 결과 반환

  해시 테이블:
  ┌─────┬─────────┐
  │ 0   │ {0,AAA} │
  └─────┴─────────┘`

  ### 2번째: c1 = 1

  `해시 테이블: {0: {0,AAA}}

  c1=1 들어옴 → 해시 테이블에 1 있나? → 없음! (Miss)
  → 후행 테이블에서 Index Scan으로 c1=1 찾기
  → 결과: {1, BBB}
  → 해시 테이블에 저장 + 결과 반환

  해시 테이블:
  ┌─────┬─────────┐
  │ 0   │ {0,AAA} │
  │ 1   │ {1,BBB} │
  └─────┴─────────┘`

  ### 3번째: c1 = 0

  `해시 테이블: {0: {0,AAA}, 1: {1,BBB}}

  c1=0 들어옴 → 해시 테이블에 0 있나? → 있음! (Hit) ⚡
  → Index Scan 안 함!
  → 저장된 {0, AAA} 바로 반환`

  ### 4번째: c1 = 1

  `c1=1 들어옴 → 해시 테이블에 1 있나? → 있음! (Hit) ⚡
  → 저장된 {1, BBB} 바로 반환`

  ### 5번째 ~ 50만번째: 전부 Hit!

  `c1=0 → Hit ⚡ → {0, AAA}
  c1=1 → Hit ⚡ → {1, BBB}
  c1=0 → Hit ⚡ → {0, AAA}
  c1=1 → Hit ⚡ → {1, BBB}
  ... (499,998번 전부 Hit!)`

  ## 왜 전부 Hit이냐면

  `값 종류가 0, 1 딱 2개
  → 처음 2번만 Miss (0 한 번, 1 한 번)
  → 3번째부터는 무조건 해시 테이블에 있음
  → 나머지 499,998번 전부 Hit!`

  ## 통계

  `전체:       500,000번
  Miss:       2번 (Index Scan 실행)
  Hit:        499,998번 (바로 반환)

  Index Scan: 단 2번!
  절약:       499,998번의 Index Scan을 안 함!`

  ## 비유

  `반 학생 50만 명의 부서를 찾아야 하는데
  부서가 0번, 1번 딱 2개뿐

  처음 2명: 부서 게시판 가서 확인 (Miss)
  → 포스트잇에 "0번=AAA, 1번=BBB" 적어둠

  나머지 499,998명: 포스트잇만 보고 바로 답변 (Hit) ⚡`


메모리가 부족하면 오래된 캐시부터 삭제하는 **LRU(Least Recently Used)** 방식으로 관리됩니다. 최근에 안 쓴 것부터 버리는 거예요.

## 예제별 분석

### 예제 1: 최적의 상황

바로 위 상황 (중복이 많은 예제)

- T1의 C1 값 종류: **2개** (0과 1)
- 50만 건 중 실제 조인: **2번** (Miss)
    - 여기서 조인은, 후행 테이블에서 Index Scan 하는걸 말함
- 나머지: **499,998번** 캐시 재사용 (Hit)
- 실행 시간: **225ms** → 매우 빠름

### 예제 2: 메모리 부족 (work_mem = 64KB)

- 설명

  ### 상황

  `T1 (50만 건, 선행): c1 값 종류 500개 (0~499)
  T2 (5천 건, 후행): 인덱스 있음
  work_mem = 64KB → 아주 작음!`

  ### 문제: 64KB에 500개 결과를 다 못 담아요

  `해시 테이블 용량: 약 50개만 저장 가능 (64KB)
  필요한 저장 수: 500개

  500개 >> 50개 → 넘침! 💥`

  ### 실행 과정

  `[1번째]   c1=0   → Miss → Index Scan → 저장
  [2번째]   c1=1   → Miss → Index Scan → 저장
  ...
  [50번째]  c1=49  → Miss → Index Scan → 저장 → 메모리 꽉 참!

  해시 테이블: (꽉 참!)
  ┌─────┬─────────┐
  │ 0   │ 결과    │
  │ 1   │ 결과    │
  │ ... │ ...     │
  │ 49  │ 결과    │  ← 50개로 가득!
  └─────┴─────────┘

  [51번째]  c1=50  → Miss → 저장하려는데 공간 없음!
  → LRU에서 가장 오래된 Key:0 삭제 (Eviction!)
  → c1=50 저장

  [52번째]  c1=51  → Miss → Key:1 삭제 → c1=51 저장
  ...
  [500번째] c1=499 → Miss → 또 삭제 → 저장`

  ### 여기까지 500번 전부 Miss

  `500개 값을 다 봤지만
  한 번에 50개만 저장 가능하니까
  뒤에 것 넣으려면 앞에 것을 계속 삭제

  해시 테이블에 남은 것: 450~499 (최근 50개만)
  삭제된 것: 0~449 (전부 밀려남)`

  ### 501번째부터: 또 Miss!

  `[501번째] c1=0 → 해시 테이블에 있나? → 이미 삭제됨! → Miss 😱
  → 또 Index Scan → Key:450 삭제 → c1=0 저장

  [502번째] c1=1 → 삭제됐음 → Miss 😱
  → 또 Index Scan → Key:451 삭제 → c1=1 저장

  ... 계속 반복

  이전 값을 저장하면 → 최근 값이 삭제됨
  최근 값이 오면 → 다시 Miss
  → 영원히 Hit가 안 남! 😱`

  ### 통계

  `전체:       500,000번
  Hits:       0번 (캐시 재사용 한 번도 못함!)
  Evictions:  49,532번 (삭제 횟수)
  Index Scan: 500,000번 (매번 실행!)`

  ## 비유

  `포스트잇이 아주 작아서 답 50개만 적을 수 있는데
  외워야 할 답이 500개

  1~50번 적음 → 51번 적으려면 1번 지움
  52번 적으려면 2번 지움
  ...
  다시 1번이 필요하면? → 이미 지워짐! → 또 찾아야 함

  → 적고 지우고 적고 지우고... 메모하는 의미가 없음!`

- T1의 C1 값 종류: **500개**
- work_mem이 너무 작아서 500개를 다 담지 못함
    - 해시테이블 용량이 제한되는 상황.
    - LRU 에 따라 계속 해시테이블 갱신됨
- **Hits: 0** → 캐시 재사용 한 번도 못함
- **Evictions: 49,532** → 메모리 부족으로 기존 캐시를 계속 삭제
- 결국 Memoize를 쓰는 의미가 없어짐

이걸 비유하면, 메모장이 너무 작아서 답을 적어도 새 답을 적으려면 이전 답을 지워야 하는 상황이에요. 지우고 적고를 반복하니 메모하는 의미가 없는 거죠.

### 예제 3: 데이터가 너무 큰 경우

- 긴 문자열 데이터(md5 × 60)를 저장하려 함
- 데이터 하나가 너무 커서 메모리에 **아예 담을 수가 없음**
- **Overflows: 100** → 메모리 초과 발생
- Evictions과 다른 점: Evictions은 "지우면서라도 시도", Overflows는 "아예 불가능"

### 해결: work_mem = 20MB로 증가

- **Hits: 49,500 / Misses: 500** → 정상적으로 캐싱 성공
- Evictions: 0, Overflows: 0 → 메모리 충분

## 핵심 정리

Memoize 조인이 효과적인 조건은 **중복이 많고, 메모리가 충분할 때**입니다. 조인키 값의 종류가 적을수록(중복이 많을수록) 캐시 히트율이 올라가고, 실제 조인 횟수가 극적으로 줄어듭니다. 하지만 work_mem이 부족하면 캐시가 무력화되니, 적절한 메모리 설정이 함께 필요합니다!
