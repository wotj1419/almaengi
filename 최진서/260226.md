# 6.1.3 Anti 조인

한마디로 **"상대방 테이블에 없는 것만 찾아줘"** 라는 조인입니다.

<aside>
💡

쿼리에 NOT EXISTS : Anti 조인

</aside>

### 비유로 이해하기

1반 명단(T1)과 2반 명단(T2)이 있다고 해봅시다.

- **일반 조인**: 1반과 2반에 **둘 다 있는** 학생을 찾아줘
- **Anti 조인**: 1반에는 있는데 **2반에는 없는** 학생을 찾아줘

## SQL로 보면

```sql
SELECT c1 FROM t1
WHERE t1.c2 < 100
AND NOT EXISTS (SELECT c1 FROM t2 WHERE t1.c1 = t2.c1);
```

이 쿼리가 하는 일은:

1. T1에서 `c2 < 100`인 행을 먼저 추출 (594건)
2. 그 594건 각각에 대해 T2에 **같은 c1 값이 있는지** 확인
3. T2에 **없는 것만** 결과로 반환 (297건)

## 핵심 특성: 찾으면 바로 멈춤

Anti 조인의 중요한 특성은, 후행 테이블에서 일치하는 행을 **하나라도 찾으면 즉시 멈춘다**는 것입니다.

<aside>
💡

Inner 조인은 후행테이블(ex. t2) 에 a=1, a=2, … 처럼 데이터(1,2) 가 여러개 존재할 수 있어서 t2를 한바퀴 다 돌아야 한다.

하지만 Anti 조인은 있으면 멈추면 되므로 한바퀴 다 돌 필요가 없다.

</aside>

비유로 설명하면:

> "2반에 김철수가 있어?"라고 물었을 때,
명단 3번째에서 김철수를 발견하면 → **"있네, 끝!"** (더 안 봄)
명단 끝까지 봤는데 없으면 → **"없네, 이 학생 결과에 포함!"**
>

일치하는 걸 찾는 순간 "이건 제외 대상"이라는 걸 알 수 있으니까, 더 볼 필요가 없는 거예요.

## 예제 데이터 구조

```
T1 (6천 건): c1 값 = a, b, c, d, e, f
T2 (3만 건): c1 값 = a, b, c (만 존재)
```

그래서 T1에서 c1이 **d, e, f**인 행들은 T2에 없으니까 Anti 조인 결과로 나오는 거예요.

## 실행 계획 분석

```
Nested Loop Anti Join
  → Seq Scan on t1 → 594건 추출 (c2 < 100 필터)
  → Index Only Scan on t2 → 594번 반복 (loops=594)
```

T1에서 594건을 추출하고, **594건 각각에 대해** T2 인덱스를 한 번씩 확인합니다.

## PostgreSQL vs Oracle 차이

여기서 흥미로운 차이점이 있어요.

**Oracle의 경우:**

T1의 c1 값 종류는 a, b, c, d, e, f 총 **6가지**잖아요? Oracle은 `NOT EXISTS`를 처리할 때 "이 값이 T2에 있는지 없는지"만 판단하면 되니까, **distinct 값 6건만** 반복 조인합니다.

```
a → T2에 있음 (한 번만 확인하면 됨)
b → T2에 있음
c → T2에 있음
d → T2에 없음 ✅
e → T2에 없음 ✅
f → T2에 없음 ✅
→ 총 6번만 조인
```

**PostgreSQL의 경우:**

같은 `NOT EXISTS`인데도 **추출된 594건 전부** 반복 조인합니다.

```
1번째 행(c1='a') → T2 확인
2번째 행(c1='a') → T2 확인  ← 같은 'a'인데 또 확인
3번째 행(c1='b') → T2 확인
...
594번째 행 → T2 확인
→ 총 594번 조인
```

같은 'a' 값이 여러 번 나와도 매번 T2를 다시 확인하는 거예요. Oracle보다 비효율적인 부분이죠. 다만 594건 정도는 인덱스로 빠르게 처리되니 실행 시간은 **1.2ms**로 매우 빠릅니다.

## Left Join으로도 같은 결과 (+ IS NULL)

```sql
SELECT t1.c1 FROM t1 LEFT JOIN t2 ON t1.c1 = t2.c1
WHERE t1.c2 < 100 AND t2.c1 IS NULL;
```

이 쿼리도 PostgreSQL이 내부적으로 **Nested Loop Anti Join**으로 변환해서 동일하게 실행합니다. `NOT EXISTS`든 `LEFT JOIN + IS NULL`이든 PostgreSQL은 같은 실행 계획을 만든다는 뜻이에요.

<aside>
💡

Left Join : Inner 조인 + null 포함 모든 데이터

Left Join에 where … is null 추가 : null 인 데이터(= 없는 데이터) 만 추출하는 것

NOT EXIST == LEFT JOIN + IS NULL

(같은 결과, 다른 작성법)

</aside>

## 핵심 정리

Anti 조인은 **"없는 것을 찾는"** 조인이고, 일치하는 행을 발견하면 즉시 멈추는 효율적인 특성이 있습니다. `NOT EXISTS`와 `LEFT JOIN + IS NULL` 두 가지 방식으로 작성할 수 있고, PostgreSQL에서는 둘 다 같은 실행 계획으로 처리됩니다. 다만 Oracle과 달리 PostgreSQL은 중복 값에 대해서도 매번 반복 조인한다는 점이 차이입니다.

# 6.1.4 Semi 조인

Anti 조인의 **반대**입니다.

<aside>
💡

쿼리에 EXISTS : Semi 조인

</aside>

- **Anti 조인**: 상대방 테이블에 **없는 것**만 찾아줘
- **Semi 조인**: 상대방 테이블에 **있는 것**만 찾아줘

## 비유로 이해하기

1반 명단(T1)과 2반 명단(T2)이 있을 때:

- **Anti 조인 (NOT EXISTS)**: 1반에는 있는데 2반에는 **없는** 학생 → d, e, f
- **Semi 조인 (EXISTS)**: 1반에도 있고 2반에도 **있는** 학생 → a, b, c

## 일반 조인과 뭐가 다른 거야?

이게 중요한 포인트예요.

`T1: a가 100건
T2: a가 10,000건`

**일반 조인 (INNER JOIN):**
T1의 a 100건 × T2의 a 10,000건 = **100만 건** 결과 발생

**Semi 조인 (EXISTS):**
T1의 a 100건 각각에 대해 T2에 a가 **있는지만** 확인 → 있으면 바로 멈춤 → **100건** 결과

Semi 조인은 후행 테이블에서 일치하는 행을 **하나만 찾으면 즉시 멈추고**, 후행 테이블의 데이터를 **반환하지도 않습니다.** "있다"는 사실만 확인하면 되니까요.

## 실행 계획 분석

`Nested Loop Semi Join
  → Seq Scan on t1 → 594건 추출 (c2 < 100 필터)
  → Index Only Scan on t2 → 594번 반복 (loops=594)`

Anti 조인 때와 **완전히 같은 구조**예요.

| 구분 | Anti 조인 | Semi 조인 |
| --- | --- | --- |
| SQL | NOT EXISTS | EXISTS |
| 의미 | T2에 없는 것 반환 | T2에 있는 것 반환 |
| 반복 횟수 | 594번 | 594번 |
| 결과 건수 | 297건 | 297건 |
| 실행 시간 | 1.2ms | 1.3ms |

둘 다 594건 전체에 대해 반복 조인하고, 찾으면 즉시 멈추는 동작도 같습니다. 차이는 **"있으면 반환" vs "없으면 반환"** 뿐이에요.

## 성능 최적화 포인트

교재에서 강조하는 핵심은 이겁니다:

**EXISTS든 NOT EXISTS든**, PostgreSQL에서는 선행 테이블의 **추출 건수만큼** 후행 테이블을 반복 조인합니다. 따라서:

**후행 테이블에 인덱스가 있으면** → 인덱스로 빠르게 존재 여부 확인 → 빠름 (예제처럼 1.3ms)

**후행 테이블에 인덱스가 없으면** → 매번 전체 스캔 → 594번 × 전체 스캔 = 매우 느림

그래서 EXISTS, NOT EXISTS를 쓸 때는 항상 **후행 테이블의 조인키에 인덱스가 있는지** 확인하는 것이 중요합니다!

<aside>
💡

ANTI, SEMI 뿐 아니라 모든 NL 조인에서 인덱싱이 중요하다.

</aside>

# 6.1.5 Lateral Join

한마디로 **"서브쿼리 안에서 바깥 테이블의 값을 쓸 수 있게 해주는 조인"**입니다.

## 먼저 문제 상황을 이해하기

보통 인라인 뷰(FROM 절의 서브쿼리)는 **독립적**이에요. 바깥 테이블을 참조할 수 없습니다.

```sql
SELECT *
FROM t1, (SELECT c1, max(c2)
          FROM t2
          WHERE t1.c2 = t2.c2   -- ❌ 에러! t1을 여기서 못 씀
          GROUP BY c1) v1
WHERE t1.c2 BETWEEN 1 AND 10;
```

이건 비유하면 이런 상황이에요:

> 선생님(t1)이 교실 밖에 있고, 학생(t2)이 교실 안에서 시험을 보는데,
학생이 "선생님 답안지 보여주세요"라고 하는 격 → **불가능!**
>

## Lateral을 붙이면?

```sql
SELECT *
FROM t1, LATERAL (SELECT c1, max(c2)
                  FROM t2
                  WHERE t1.c2 = t2.c2   -- ✅ 이제 가능!
                  GROUP BY c1) v1
WHERE t1.c2 BETWEEN 1 AND 10;
```

`LATERAL` 키워드를 붙이면 서브쿼리가 바깥 테이블의 **각 행마다** 실행되면서, 바깥 값을 참조할 수 있게 됩니다.

> 선생님이 교실 안으로 들어와서 한 명씩 옆에 앉아줌 → 학생이 선생님 답안지를 볼 수 있음
>

## 동작 방식

```
T1에서 1번째 행 꺼냄 (c2 = 10)
  → c2=10을 서브쿼리에 전달
  → T2에서 c2=10인 행들을 찾아서 GROUP BY, MAX 수행
  → 결과 반환

T1에서 2번째 행 꺼냄 (c2 = 20)
  → c2=20을 서브쿼리에 전달
  → T2에서 c2=20인 행들을 찾아서 GROUP BY, MAX 수행
  → 결과 반환

... T1의 모든 행에 대해 반복
```

그래서 내부적으로 **항상 Nested Loop**로 처리됩니다. T1의 각 행마다 서브쿼리를 실행하는 구조이니까요.

## 실행 계획 분석

```
Nested Loop
  → Seq Scan on t1 → 18건 추출
  → GroupAggregate → loops=18 (18번 반복 실행)
    → Index Scan using t2_idx2 on t2 → T2 인덱스 사용
```

핵심은 T1에서 전달된 c2 값이 서브쿼리 안으로 들어가서 **T2의 인덱스(t2_idx2)를 탈 수 있게 된다**는 점이에요. 이걸 **Push Predicate**라고 합니다. 조건이 서브쿼리 안으로 "밀려 들어가는" 거죠.

인덱스가 없으면 18번 반복할 때마다 T2 전체를 스캔해야 하니까, **후행 테이블의 조인 컬럼에 인덱스가 있는지**가 성능의 핵심입니다. (NL 조인의 원칙과 같죠!)

## Left Join Lateral

```sql
SELECT *
FROM t1 LEFT JOIN LATERAL (...) v1 ON TRUE
WHERE t1.c2 BETWEEN 1 AND 10;
```

일반 Lateral은 서브쿼리 결과가 없으면 해당 T1 행이 **제외**되지만, Left Join Lateral은 결과가 없어도 T1 행을 **유지하고 NULL로 채워줍니다.**

`ON TRUE`는 "추가 조인 조건 없이 항상 연결해라"는 뜻이에요. 실제 조인 조건은 이미 서브쿼리 안의 WHERE에 들어있으니까요.

## 언제 쓰면 좋을까?

Lateral 조인은 이런 상황에서 유용합니다:

- 각 행마다 **GROUP BY, 집계 함수**를 적용하고 싶을 때
- 각 행마다 **TOP N**을 뽑고 싶을 때 (예: 고객별 최근 주문 3건)
- 상관 서브쿼리 결과를 **여러 컬럼으로** 받고 싶을 때

예를 들어 "고객별 최근 주문 3건"을 구하려면:

```sql
SELECT c.*, recent.*
FROM customers c
LEFT JOIN LATERAL (
    SELECT order_id, order_date, amount
    FROM orders o
    WHERE o.customer_id = c.customer_id
    ORDER BY order_date DESC
    LIMIT 3
) recent ON TRUE;
```

이런 쿼리는 일반 조인으로는 작성하기 어렵지만, Lateral 조인으로 깔끔하게 해결할 수 있다.

# 6.1.6 Parallel Mode (병렬 모드)

한마디로 **"일꾼 여러 명이 나눠서 일하자"**입니다.

보통 쿼리는 CPU 코어 **1개**가 처리하는데, Parallel 모드에서는 **여러 코어가 동시에** 처리합니다.

## 비유로 이해하기

이사할 때 짐을 나른다고 생각해 보세요.

- **Non-Parallel**: 혼자서 박스 100개를 나름 → 오래 걸림
- **Parallel**: 3명이서 박스를 나눠서 나름 → 빠르게 끝남

## 3단계 처리 과정

### 1단계: 분할 (Distribution)

테이블 데이터를 **블록 단위로 나눠서** 각 워커에게 배분합니다.

```
T1 테이블 (100만 건)
  → 워커1: 1~33만 건 담당
  → 워커2: 34~66만 건 담당
  → 리더:  67~100만 건 담당
```

### 2단계: 조인 처리 (Join Processing)

각 워커가 **자기 몫을 독립적으로** 조인합니다.

```
워커1: 자기가 받은 33만 건으로 T2와 NL 조인
워커2: 자기가 받은 33만 건으로 T2와 NL 조인
리더:  자기가 받은 34만 건으로 T2와 NL 조인
(동시에 진행!)
```

### 3단계: 결과 병합 (Merge Results)

각 워커의 결과를 **리더 프로세스가 모아서** 최종 결과를 만듭니다.

```
워커1 결과 ─┐
워커2 결과 ─┼→ 리더가 합침 → 최종 결과
리더 결과  ─┘
```

## 예제 성능 비교

| 모드 | 실행 시간 |
| --- | --- |
| Non-Parallel (혼자) | **23,553ms** (약 24초) |
| Parallel (워커2 + 리더1 = 3명) | **17,070ms** (약 17초) |
| Parallel (워커2만, 리더 미참여) | **약 30초** |

## 리더 프로세스 참여가 왜 중요해?

실행 계획에서 `loops=3`이 나오면 워커 2개 + 리더 1개 = **3명이 일한 것**입니다.

`parallel_leader_participation = off`로 끄면 `loops=2`가 되고, 리더는 **결과를 모으기만** 합니다.

비유하면:

- **리더 참여 (on)**: 팀장도 같이 짐 나르면서 관리도 함 → **17초**
- **리더 미참여 (off)**: 팀장은 지켜보면서 관리만 함 → **30초**

팀장도 일하면 거의 **2배 빠른** 거예요!

## 항상 Parallel이 좋은 거 아니야?

아닙니다. 다음 상황에서는 오히려 비효율적이거나 사용 불가합니다.

**데이터가 적을 때**: 3명이 나눠서 할 만큼의 일이 아니면, 일을 나누고 결과를 합치는 **오버헤드만 낭비**됩니다. 혼자 하는 게 더 빠를 수 있어요.

**지원하지 않는 작업들**:

- CREATE TABLE AS SELECT
- SELECT INTO
- CREATE MATERIALIZED VIEW
- REFRESH MATERIALIZED VIEW

## 주요 파라미터 쉽게 정리

| 파라미터 | 쉬운 설명 | 기본값 |
| --- | --- | --- |
| `max_parallel_workers_per_gather` | 쿼리 하나에 최대 몇 명 투입? | 2 |
| `max_parallel_workers` | 서버 전체에서 최대 몇 명? | 8 |
| `parallel_tuple_cost` | 워커 간 데이터 전달 비용 (낮을수록 병렬 선호) | 0.1 |
| `parallel_leader_participation` | 팀장도 일할까? | on |
| `min_parallel_table_scan_size` | 테이블이 최소 이 크기여야 병렬 고려 | 8MB |

`max_parallel_workers_per_gather = 0`으로 설정하면 Parallel 모드가 **완전히 비활성화**됩니다. 앞의 Materialize, Memoize 예제에서 이 값을 0으로 설정한 이유가 바로 병렬 처리를 끄고 순수한 NL 조인 동작만 보기 위해서였습니다.
