# Spring Batch 핵심 개념

Spring Batch는 **“정해진 시간/조건에 대량 데이터를 안정적으로 처리하는 프레임워크”**예요.  
예: 월급 정산, 정산 파일 생성, 정산 결과 발송, 정기 통계 집계 등.

---

## 1) 기본 구조 한눈에 보기

```text
Job (배치 작업 1개 = 큰 업무 1개)
 ├─ Step 1 (1단계)
 │   ├─ ItemReader    : 데이터 읽기
 │   ├─ ItemProcessor : 가공/계산
 │   └─ ItemWriter    : 저장/출력
 └─ Step 2 (2단계)
     └─ Tasklet       : 단순 단일 작업
````

---

## 2) 핵심 용어 (진짜 많이 쓰는 것들)

### Job

* 배치 작업의 **최상위 단위**
* “월급 정산 Job”, “홈택스 신고 파일 생성 Job”처럼 **업무 덩어리 하나**라고 보면 돼요.

### Step

* Job 안에 들어있는 **실행 단계**
* 하나의 Job은 Step을 여러 개 가질 수 있고, 보통 **순서대로 실행**돼요.

---

## 3) Step을 만드는 두 가지 방식

### A. Chunk 기반 처리 (대량 데이터 처리의 표준 패턴)

데이터를 **N건씩 묶어서** 처리해요.

**흐름**

1. Reader가 데이터를 1건씩 읽음
2. N건이 모이면 Processor가 가공
3. Writer가 N건을 저장/출력
4. **커밋(Commit)** 하고 다음 N건 처리

```text
[Read 1] → [Read 1] → ... → (N개 모임)
→ [Process N] → [Write N] → Commit
```

예: `chunk size = 50`이면

* 직원 50명 읽기 → 50명 급여 계산 → 50명 저장 → 커밋
* 다음 50명 반복

#### ItemReader

* 데이터를 “어디서” 읽을지 결정
* 예: DB 조회, 파일 읽기, API 호출

#### ItemProcessor

* 읽은 데이터를 “어떻게” 바꿀지/계산할지
* 예: 급여 계산, 필터링(불필요한 데이터 제외), 포맷 변환

#### ItemWriter

* 결과를 “어디에” 쓸지
* 예: DB 저장(INSERT/UPDATE), 파일 생성, 메시지 발송 요청

---

### B. Tasklet (단순 작업용)

Chunk 패턴이 필요 없을 때 씁니다.

* 예: 파일 삭제, 특정 테이블 초기화, 알림 한 번 보내기, “한 번에 끝나는” 작업

---

## 4) 알맹이 프로젝트에 대입해보기 (예시)

### [급여 정산 Job]

#### Step 1: 근태 집계 + 급여 계산 (Chunk 방식이 잘 맞음)

* **Reader**: Attendances에서 해당 월 출퇴근 로그 조회
* **Processor**: 주휴수당, 연장/야간, 공제 계산
* **Writer**: Payrolls + Payroll_Details 저장

#### Step 2: 명세서 발송 (Tasklet이 깔끔함)

* **Tasklet**: 카카오톡/SMS로 명세서 링크 일괄 발송

---

## 5) Spring Batch가 “대신” 해주는 것들 (운영에서 핵심)

| 기능        | 설명                                       |
| --------- | ---------------------------------------- |
| 자동 재시작    | 3번째 청크에서 실패 → 재실행하면 **그 지점부터 이어서 처리** 가능 |
| 스킵 정책     | 특정 직원 데이터 오류 → **그 건만 건너뛰고** 나머지는 계속     |
| 재시도       | DB 연결 같은 일시 오류 → **N번 재시도** 후 실패 처리      |
| 메타 테이블 기록 | 실행 이력/상태를 DB에 자동 기록                      |
| 병렬 처리     | 예: 매장별 파티셔닝으로 멀티스레드 처리 가능                |

## 6) JobRepository (메타 테이블: 실행 이력 저장소)

Spring Batch는 실행 이력을 **DB에 자동으로 기록**합니다.
그래서 “어디서 멈췄지?”를 바로 추적할 수 있어요.

대표 테이블들:

* **BATCH_JOB_INSTANCE**

    * “어떤 Job이 어떤 파라미터로 생성되었는지” (Job의 ‘인스턴스’ 개념)

* **BATCH_JOB_EXECUTION**

    * Job이 **언제 실행됐고**, 성공/실패했는지, 상태/시간 정보

* **BATCH_STEP_EXECUTION**

    * Step별 처리 건수, 스킵 건수, 소요 시간 등 “디테일 로그”

> 덕분에 “1월 정산 Job 실패했는데 어디까지 했지?” 같은 상황에서
> **중단 지점 확인 + 이어서 재실행**이 가능해집니다.

---

## 7) 실행 트리거(스케줄) — “언제 돌릴지”는 별도

Spring Batch는 **실행 자체의 프레임워크**이고,
“언제 실행할지”는 다른 방법으로 연결해야 합니다.

대표 방식:

* `@Scheduled(cron = "0 0 0 1 * *")`
  → 매월 1일 00:00 실행

* 사장님이 관리자 페이지에서 “정산 실행” 버튼 클릭
  → API로 Job 실행 트리거

* Jenkins / Airflow / Kubernetes CronJob 같은 외부 스케줄러
  → 정해진 시간에 Job 실행 호출

---

## 8) 한 문장으로 요약

* **Job** = 큰 배치 업무 1개
* **Step** = 그 업무의 단계들
* **Chunk** = 대량 데이터는 N건씩 안정적으로 처리
* **Tasklet** = 한 번에 끝나는 단순 작업
* **JobRepository** = 실행 이력 저장 → 재시작/추적 가능
