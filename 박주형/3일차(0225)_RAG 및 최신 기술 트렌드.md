## 1. RAG란 무엇인가

RAG(Retrieval-Augmented Generation)는 LLM이 자체 학습 데이터만으로 답변하는 것이 아니라, **외부 문서 데이터베이스에서 관련 내용을 검색(Retrieve)한 뒤 이를 근거로 답변을 생성(Generate)하는 방식**이다.

비유하자면 "오픈북 시험"과 같다. 모델이 답을 쓰기 전에 관련 자료를 먼저 찾아보고, 그 자료를 근거로 답변을 작성하는 구조이다.

### 1.1 RAG가 해결하는 문제

LLM은 학습 종료 시점(knowledge cutoff) 이후의 정보를 알 수 없고, 도메인 특화 지식이 부족하며, 환각(hallucination) 현상이 발생할 수 있다. RAG는 이러한 한계를 외부 지식 검색으로 보완한다.

| LLM의 한계 | RAG의 해결 방식 |
| --- | --- |
| 학습 이후 최신 정보 부재 | 외부 문서 DB에서 최신 정보를 검색하여 반영 |
| 도메인 특화 지식 부족 | 도메인 문서(법령, 매뉴얼 등)를 벡터DB에 적재하여 검색 |
| 환각 (Hallucination) | 검색된 근거 문서를 기반으로 답변 생성 → 사실 기반 응답 |
| 정보 출처 불투명 | 검색 문서의 출처를 함께 제공 → 응답의 신뢰성 확보 |

### 1.2 RAG 기본 동작 흐름

```
사용자 질문
    ↓
[1] 질문 임베딩 (Query Embedding)
    ↓
[2] 벡터DB에서 유사 문서 검색 (Retrieval)
    ↓
[3] 검색된 문서 + 질문을 LLM에 전달 (Augmentation)
    ↓
[4] LLM이 근거 기반 답변 생성 (Generation)
    ↓
응답 (+ 출처 표시)
```

### 1.3 RAG 파이프라인의 주요 구성 요소

| 단계 | 구성 요소 | 설명 |
| --- | --- | --- |
| **데이터 수집** | Document Loader | PDF, DOCX, HTML, CSV 등 다양한 문서 포맷 로딩 |
| **전처리** | Chunking | 문서를 검색 가능한 단위(청크)로 분할 |
| **임베딩** | Embedding Model | 텍스트를 벡터(숫자 배열)로 변환 |
| **저장** | Vector DB | 임베딩된 벡터를 저장하고 유사도 검색 제공 (Pinecone, ChromaDB, Weaviate 등) |
| **검색** | Retriever | 질문과 의미적으로 유사한 문서 청크를 검색 |
| **후처리** | Reranker | 검색 결과의 관련성을 재평가하여 순위 재조정 |
| **생성** | LLM (Generator) | 검색된 문서를 컨텍스트로 받아 최종 답변 생성 |

## 2. 청킹(Chunking) 전략

청킹은 RAG 파이프라인의 첫 번째 관문으로, 검색 품질에 직접적인 영향을 미친다. 청크가 너무 작으면 문맥이 유실되고, 너무 크면 검색 정밀도가 떨어진다.

### 2.1 고정 크기 청킹 (Fixed-Size Chunking)

가장 단순한 방법으로, 문서를 일정 글자 수(예: 500자) 또는 토큰 수로 기계적으로 분할한다. 오버랩(overlap)을 두어 청크 경계에서 문맥이 끊기는 것을 완화한다.

- **장점:** 구현이 간단하고 처리 속도가 빠름
- **단점:** 하나의 개념이 두 청크로 쪼개지거나, 관련 없는 내용이 한 청크에 섞일 수 있음

### 2.2 시맨틱 청킹 (Semantic Chunking)

문장 간 임베딩 유사도를 계산하여 **의미가 바뀌는 지점에서 분할**하는 방식이다. 같은 주제의 내용은 하나의 청크로 묶이므로 검색 품질이 향상된다.

- **장점:** 의미 단위 보존으로 검색 재현율(recall) 최대 9% 향상 (고정 크기 대비)
- **단점:** 임베딩 계산이 필요해 처리 비용이 증가

```
[고정 크기 청킹]
"...주휴수당은 1주 동안 소정근로일을 | 개근한 근로자에게 1주일에 평균 1회..."
→ 문장 중간에서 잘림 → 검색 시 불완전한 정보 반환

[시맨틱 청킹]
"주휴수당은 1주 동안 소정근로일을 개근한 근로자에게 1주일에 평균 1회 이상의
유급휴일을 부여하는 것을 말한다. 주 15시간 이상 근무 조건을 충족해야 한다."
→ 의미 단위로 묶임 → 검색 품질 향상
```

### 2.3 구조 기반 청킹 (Document Structure-Based Chunking)

문서 자체의 구조(마크다운 헤더, HTML 태그, PDF 섹션 등)를 기준으로 분할한다. 법률 문서처럼 조/항/호 구조가 명확한 문서에 특히 효과적이다.

### 2.4 Parent-Child 청킹

검색은 작은 "자식(child)" 청크 단위로 하되, LLM에 전달할 때는 더 큰 "부모(parent)" 블록을 함께 전달하여 문맥을 보존하는 전략이다. 검색 정밀도와 문맥 보존을 동시에 달성할 수 있다.

## 3. 검색(Retrieval) 전략

### 3.1 Dense Retrieval (밀집 검색)

텍스트를 벡터로 변환하여 벡터 공간에서 유사도(코사인 유사도 등)를 계산하는 방식이다. 의미적으로 유사한 문서를 찾는 데 강하다.

- **장점:** "여행 경비"와 "trip budget"처럼 표현이 달라도 의미가 같으면 검색 가능
- **단점:** "제60조", "15시간" 같은 정확한 키워드 매칭에는 약할 수 있음

### 3.2 Sparse Retrieval (희소 검색 / BM25)

전통적인 키워드 기반 검색. 정확한 용어가 일치하는 문서를 찾는 데 강하다.

- **장점:** 법률 조문 번호, 수치 등 정확한 키워드 매칭에 강함
- **단점:** 동의어나 의미적 유사성을 파악하지 못함

### 3.3 하이브리드 검색 (Hybrid Retrieval)

Dense + Sparse 검색을 결합한 방식으로, 현재 실무에서 가장 많이 사용되는 표준 접근법이다. 의미적 유사성과 키워드 정확도를 동시에 확보할 수 있다.

```
사용자 질문: "주 15시간 미만 알바도 주휴수당 받을 수 있나요?"

[Dense 검색] → 의미적으로 "주휴수당 조건" 관련 문서 검색
[Sparse 검색] → "15시간", "주휴수당" 키워드가 포함된 문서 검색
[결합] → 두 결과를 합산·재정렬하여 최종 검색 결과 도출
```

### 3.4 Reranking (리랭킹)

초기 검색으로 가져온 후보 문서(수십~수백 개)를 Cross-Encoder 모델로 재평가하여 가장 관련성 높은 문서만 선별하는 후처리 단계이다.

- 정밀도 10~30% 향상 효과 (약 50~100ms의 추가 지연 발생)
- 대표적인 모델: Cohere Reranker, bge-reranker 등

## 4. 최신 RAG 아키텍처

### 4.1 GraphRAG (지식 그래프 기반 RAG)

Microsoft가 2024년 오픈소스로 공개한 방식으로, 문서에서 엔티티(개체)와 관계를 추출하여 **지식 그래프를 구축**하고, 그래프 순회를 통해 검색하는 방식이다.

**기존 RAG의 한계:**
일반적인 벡터 검색은 개별 사실(local query)을 찾는 데는 강하지만, "이 문서 전체에서 주요 테마가 뭔가?" 같은 글로벌 질문이나 여러 문서에 걸친 관계 파악에는 약하다.

**GraphRAG의 해결 방식:**
1. 문서에서 엔티티(사람, 조직, 개념 등)와 관계를 LLM으로 추출
2. 엔티티-관계 지식 그래프 구축
3. 커뮤니티 감지 알고리즘으로 관련 엔티티를 그룹화
4. 쿼리 시 그래프 순회를 통해 직간접적으로 관련된 정보를 탐색

**노동법 도메인 적용 예시:**
```
[지식 그래프]
주휴수당 ──조건──→ 주 15시간 이상 근무
    │                    │
    ├──관련법──→ 근로기준법 제55조
    │                    │
    └──연관──→ 4대보험 ──조건──→ 월 60시간 이상
                         │
                         └──관련법──→ 국민연금법 시행령

질문: "알바생이 주 16시간 일하면 어떤 의무가 생기나요?"
→ 그래프 순회로 주휴수당 + 관련 법조항을 한꺼번에 검색
```

**특징:**
- 구조화된 도메인에서 검색 정밀도 최대 99%까지 달성 가능
- 단점: 그래프 구축 시 대량의 LLM 토큰 소비 (원본 텍스트의 수배~수십배)

### 4.2 Agentic RAG (에이전트 기반 RAG)

고정된 단일 검색이 아니라, **자율 에이전트가 멀티스텝 추론**을 수행하는 방식이다. 에이전트가 질문을 분석하고, 어떤 도구를 사용할지 계획하고, 중간 결과를 평가하며, 필요하면 추가 검색을 수행한다.

**기존 RAG와의 차이:**

| | 기존 RAG | Agentic RAG |
| --- | --- | --- |
| 검색 방식 | 단일 검색 (Single-shot) | 멀티스텝 검색 (Plan → Act → Observe → Reflect) |
| 쿼리 처리 | 질문을 그대로 검색 | 질문을 분해하여 서브쿼리로 나눠 검색 |
| 도구 사용 | 벡터DB 검색만 | 벡터DB + 외부 API + DB 쿼리 등 다중 도구 활용 |
| 자기 평가 | 없음 | 중간 결과를 평가하고 필요 시 재검색 |

**동작 흐름:**
```
사용자 질문: "A 알바생 4대보험 가입해야 하나요?"

[Plan] 이 질문에 답하려면 두 가지 정보가 필요해:
       (1) A 알바생의 월간 근무시간 (2) 4대보험 가입 기준

[Act 1] 매장 DB에서 A 알바생의 이번 달 근무시간 조회
        → 결과: 월 58시간

[Act 2] 벡터DB에서 "4대보험 가입 의무 조건" 검색
        → 결과: "월 60시간 이상 근무 시 4대보험 가입 의무 발생"

[Observe] 58시간 < 60시간이므로 현재는 미해당

[Reflect] 하지만 거의 기준에 근접 → 추가 정보 제공이 필요

[Generate] "현재 A 알바생은 월 58시간 근무로 4대보험 가입 의무는 없습니다.
           다만 2시간 추가 근무 시 월 60시간을 초과하여 의무가 발생하니
           스케줄 조정 시 유의해주세요."
```

**핵심 가치:** 단순히 문서를 검색하는 것을 넘어, 여러 데이터 소스(비정형 문서 + 구조화 DB)를 결합하여 맥락에 맞는 구체적인 답변을 생성할 수 있다.

### 4.3 Self-RAG (자기 반성형 RAG)

모델이 스스로 **"지금 검색이 필요한지"를 판단**하고, 생성된 응답을 자기 비판적으로 평가하여 사실성과 인용 정확도를 높이는 방식이다.

**Self-RAG의 판단 토큰:**

| 토큰 | 역할 | 예시 |
| --- | --- | --- |
| **Retrieve** | 검색이 필요한지 판단 | "이 질문은 법률 근거가 필요해 → 검색 실행" |
| **IsRelevant** | 검색된 문서가 질문에 관련 있는지 평가 | "이 문서는 주휴수당이 아니라 연차에 관한 내용 → 제외" |
| **IsSupported** | 생성한 답변이 검색 문서로 뒷받침되는지 확인 | "이 답변의 근거가 검색 문서에 있는가?" |
| **IsUseful** | 최종 답변이 사용자에게 유용한지 평가 | "질문에 충분히 답했는가?" |

**법률 도메인에서의 중요성:** 잘못된 법률 정보를 제공하면 실질적인 피해가 발생할 수 있으므로, 모델이 자기 응답의 근거 충분성을 스스로 검증하는 메커니즘이 특히 중요하다.

### 4.4 Corrective RAG (CRAG)

검색된 문서의 품질을 평가하여, 품질이 낮으면 **외부 웹 검색으로 보완**하는 방식이다.

```
질문 → 벡터DB 검색 → 문서 품질 평가
                         │
                    ┌─────┼─────┐
                    ▼     ▼     ▼
                 [양호]  [모호]  [불량]
                    │     │     │
                    │     │     └→ 웹 검색으로 대체
                    │     └→ 벡터DB 결과 + 웹 검색 결합
                    └→ 그대로 사용
```

### 4.5 Long-Context RAG (TreeRAG + GraphRAG 결합)

TreeRAG는 문서의 계층적 구조(섹션 → 하위섹션 → 문단)를 트리로 표현하여 물리적 청킹으로 인한 의미 단절을 해소한다. GraphRAG와 결합하면:

- **TreeRAG:** 문서 내부의 로컬 문맥을 계층적으로 보존
- **GraphRAG:** 문서 간 관련 내용을 엔티티 관계 기반으로 연결

두 방식을 합치면 "문서 내 문맥 보존 + 문서 간 관계 탐색"을 동시에 달성할 수 있어, 복잡한 멀티홉 질문에 대한 답변 품질이 크게 향상된다.

## 5. 시맨틱 라우팅 (Semantic Routing)

사용자 질문의 의도를 분류하여 적절한 처리 경로로 라우팅하는 기법이다. 하나의 시스템이 여러 데이터 소스를 다뤄야 할 때 특히 유용하다.

```
사용자 질문
    ↓
[의도 분류기]
    │
    ├─ 법령 질문 ("주휴수당 조건이 뭐야?")
    │   → 벡터DB (노동법 문서) 검색
    │
    ├─ 매장 데이터 질문 ("A 알바생 이번 달 근무시간?")
    │   → 매장 DB 직접 쿼리
    │
    ├─ 복합 질문 ("A 알바생 4대보험 가입해야 해?")
    │   → Agentic RAG (DB + 벡터DB 결합)
    │
    └─ 일반 대화 ("안녕하세요")
        → LLM 직접 응답
```

## 6. 주요 도구 및 프레임워크

### 6.1 RAG 프레임워크

| 프레임워크 | 특징 | 적합한 경우 |
| --- | --- | --- |
| **LangChain** | 가장 대중적, 풍부한 생태계, 다양한 통합 지원 | 빠른 프로토타이핑, 일반적인 RAG 구축 |

## 7. RAG 평가 지표

RAG 시스템의 성능을 측정하기 위한 주요 지표이다.

| 지표 | 측정 대상 | 설명 |
| --- | --- | --- |
| **Context Precision** | 검색 | 검색된 문서 중 실제로 관련 있는 문서의 비율 |
| **Context Recall** | 검색 | 관련 있는 전체 문서 중 실제로 검색된 비율 |
| **Faithfulness** | 생성 | 생성된 답변이 검색된 문서에 의해 뒷받침되는 정도 |
| **Answer Relevancy** | 생성 | 생성된 답변이 원래 질문에 얼마나 적합한지 |
| **Hallucination Rate** | 생성 | 검색 문서에 근거하지 않는 정보가 포함된 비율 |

대표적인 평가 프레임워크: **RAGAS** (RAG Assessment Score)

## 8. 2025~2026 RAG 트렌드 요약

### 8.1 핵심 트렌드

| 트렌드 | 설명 | 성숙도 |
| --- | --- | --- |
| **하이브리드 검색** | Dense + Sparse + Reranking 결합 | ✅ 실무 표준 |
| **GraphRAG** | 지식 그래프 기반 관계 탐색 | ✅ 프로덕션 도입 시작 |
| **Agentic RAG** | 에이전트가 멀티스텝 검색·추론 수행 | 🔶 빠르게 확산 중 |
| **Self-RAG** | 모델의 자기 평가·반성 메커니즘 | 🔶 연구 → 실무 전환 중 |
| **Multimodal RAG** | 텍스트 + 이미지 + 오디오 통합 검색 | 🔸 인프라 미성숙, 2026년 본격화 전망 |

### 8.2 주요 흐름

**"RAG는 죽었다"는 틀렸다.** 2025년 AI Agent가 화두가 되면서 "Agent가 RAG를 대체한다"는 주장이 있었으나, 실제로는 Agent가 RAG를 활용하는 구조로 수렴하고 있다. Agent는 "언제, 어떻게 검색할지"를 결정하고, RAG는 "검색의 정확성"을 담당하는 상호보완적 관계이다.

**RAG는 "검색 기법"에서 "컨텍스트 엔진"으로 진화하고 있다.** 단순히 문서를 검색하여 LLM에 전달하는 것을 넘어, 데이터의 수집·정제·구조화·검색·추론을 아우르는 통합 지식 인프라로 발전하고 있다.

**데이터 품질이 모델 성능보다 중요해지고 있다.** "더 많은 데이터 = 더 좋은 결과"라는 통념이 깨지고, 잘 큐레이션된 고품질 데이터셋이 대규모 비정제 데이터보다 검색 정확도와 답변 품질 모두에서 우수한 결과를 보여주고 있다.

## 9. 실무 적용 시 체크리스트

RAG 시스템을 구축할 때 단계별로 확인해야 할 사항을 정리한다.

### 청킹

- [ ] 도메인 문서의 구조를 분석하고 최적의 청킹 전략을 선택했는가 (고정/시맨틱/구조 기반)
- [ ] 청크 크기가 적절한가 (너무 작으면 문맥 유실, 너무 크면 정밀도 저하)
- [ ] 오버랩 설정을 통해 청크 경계의 정보 유실을 방지했는가

### 검색

- [ ] 하이브리드 검색(Dense + Sparse)을 적용했는가
- [ ] Reranker를 추가하여 검색 정밀도를 높였는가
- [ ] 도메인에 적합한 임베딩 모델을 선택했는가 (한국어 → Upstage 등 고려)

### 생성

- [ ] 시스템 프롬프트에 "검색된 문서에 근거해서만 답변하라"는 지시를 포함했는가
- [ ] 출처(source citation)를 응답에 포함하도록 설계했는가
- [ ] 환각 방지를 위한 장치(Self-RAG, CRAG 등)를 고려했는가

### 평가

- [ ] 평가 데이터셋(질문-정답 쌍)을 구축했는가
- [ ] RAGAS 등 프레임워크로 Context Precision, Faithfulness 등을 측정하고 있는가
- [ ] 기준선(baseline) 대비 개선 수치를 추적하고 있는가
